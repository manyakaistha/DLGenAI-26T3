6 · Keep the examination separate from the lesson

Core question: could information about a validation example have influenced the fitted rule?

Training examples teach a model. Validation examples help us compare choices such as thresholds. A final independent evaluation estimates how the chosen system behaves on new data. Reusing validation for many decisions makes it less independent, even if no gradient was calculated on it.

Core · Split images before their derivatives

One cloud photograph contributes four class rows. If those rows are shuffled separately, some labels from the same photograph can enter training and others validation. The model has already seen the image it is being examined on. Similar leakage occurs if crops, flipped copies or resized variants of the same original land on both sides.

Create one image-level table first, assign each image to one partition, and join its class rows back afterwards. If several photographs come from the same source scene or acquisition group, consider that group as the indivisible unit. An image-ID check prevents identical-ID leakage; it does not prove independence from near-duplicate scenes. Scikit-learn's leakage guidance explains why preprocessing fitted on held-out data also creates leakage.

Core · Stratification tries to preserve representation

A random split does not guarantee that rare labels appear on both sides. Stratification tries to represent selected label information in each partition. For multi-label data, one simple approach treats the entire presence vector as a combination label:

[0,0,0,0] → 0000
[1,0,0,0] → 1000
[1,0,0,1] → 1001

This preserves combinations approximately when there are enough examples. It is different from pretending that every image has one of four mutually exclusive labels. A class can belong to several combinations.

For an invented 20-image table with combination counts [8, 4, 4, 4], a 25% validation target can allocate [2, 1, 1, 1]: five validation images, with every combination represented. This convenient arithmetic does not generalise to all datasets.

Core · Rounding and rare combinations are real constraints

An actual split contains whole images. A combination appearing three times cannot place exactly 20% of itself in validation. A singleton cannot appear in both partitions without duplication and leakage. Some stratification routines reject strata with too few members; a small validation set can also be too small to hold every distinct combination.

Use a declared policy rather than hiding this problem:

  1. Count images per combination and per class before splitting.
  2. Set an image-level validation size and random seed.
  3. Use combination stratification where feasible; if necessary, use a documented rare-stratum fallback or a multi-label stratification method.
  4. Give source-group separation priority over an attractive label balance.
  5. Audit the resulting integer counts and disclose exceptions.

Grouping rare combinations into a broader splitting stratum changes only how the split is allocated; it must not erase or relabel their original targets. No method can manufacture independent examples of a class that appears only once. If a class lacks validation positives, say that its positive-case performance cannot be established on this split.

The practice notebook records its actual policy. Read that cell's printed support table rather than assuming the word “stratified” guarantees exact proportions. Scikit-learn's train_test_split reference describes its stratify and random_state arguments; it is not a general guarantee of multi-label or grouped independence.

Work through an integer allocation, not just a percentage

“Use 25% for validation” is a target, not a way to divide an individual image. Consider a fictional set of 16 independent source images. Their four presence patterns occur 7, 5, 3 and 1 times. A four-image holdout would ideally receive 7/4 = 1.75, 5/4 = 1.25, 3/4 = 0.75 and 1/4 = 0.25 images from those patterns. None of those fractions is a possible selected count. If we simply round each one to the nearest integer, we get 2+1+1+0=4 here, but independent rounding is not guaranteed to sum to the desired total in another table.

A transparent largest-remainder exercise starts with floors [1,1,0,0], then gives the two remaining validation places to the largest fractional remainders: 0.75 from the seven-image stratum and 0.75 from the three-image stratum. With a declared tie rule, the allocation is [2,1,1,0]. The singleton stays in training. That is a policy choice, not a proof that the validation set can assess the singleton's combination. Even a class present in several combinations may have poor support if their allocations all round down. Audit the class totals after allocating combinations.

The following small code spells out the policy. It operates on invented IDs and assumes those IDs are independent. It keeps at least one member of each non-singleton stratum in training; a singleton is training-only. It deliberately raises an error if that policy cannot meet the requested validation size. In a real project, that failure calls for a documented decision about holdout size or grouping, not a hidden duplicate.

import numpy as np

members = {
    "0000": [f"clean_{i}" for i in range(7)],
    "1000": [f"fish_{i}" for i in range(5)],
    "0100": [f"flower_{i}" for i in range(3)],
    "1010": ["rare_0"],
}
seed, wanted = 30, 4
rng = np.random.default_rng(seed)
counts = {key: len(ids) for key, ids in members.items()}
raw = {key: wanted * count / sum(counts.values())
       for key, count in counts.items()}
assigned = {key: int(np.floor(value)) for key, value in raw.items()}
capacity = {key: max(0, count - 1) for key, count in counts.items()}
while sum(assigned.values()) < wanted:
    choices = [key for key in sorted(members)
               if assigned[key] < capacity[key]]
    if not choices:
        raise ValueError("Declared training-support policy cannot fill holdout")
    chosen = max(choices, key=lambda key: raw[key] - assigned[key])
    assigned[chosen] += 1
validation_ids, training_ids = [], []
for key, ids in members.items():
    shuffled = rng.permutation(ids).tolist()
    validation_ids += shuffled[:assigned[key]]
    training_ids += shuffled[assigned[key]:]
assert len(validation_ids) == wanted
assert not (set(validation_ids) & set(training_ids))
assert set(validation_ids) | set(training_ids) == {
    image_id for ids in members.values() for image_id in ids
}
print(assigned)  # {'0000': 2, '1000': 1, '0100': 1, '1010': 0}

This toy method explains allocation; it is not a general grouped multi-label splitter. A code path that first divides photographs into tiles and then “stratifies” the tiles still leaks source images. If two images are from one acquisition group, replace the image IDs with group IDs before this reasoning. A group can have several labels and several images, so group counts and image counts will differ. Check both, and keep the group intact even when doing so makes the label balance untidy.

What combination and per-class balancing preserve

A four-bit vector records which of four labels occur somewhere in an image. Combination stratification treats 1001 as its own stratum, so it can preserve the frequency of that co-occurrence when the stratum is sufficiently populated. It does not preserve mask size, severity, location, acquisition source or pixel overlap. Two 1001 images might have very different marked areas. The vector also says nothing about whether their two masks intersect at any pixel.

An iterative multi-label allocator instead tries to balance each class's positive count across partitions, often paying special attention to rare labels first. That can retain marginal class support when many whole combinations are singletons. It may nevertheless change the frequency of specific combinations. Neither method guarantees exact balance with whole images, and neither repairs duplicate-source leakage. A grouped split can satisfy independence while some classes have zero validation support. This is a limitation to state and investigate, not permission to split one source across both sets.

Decision Preserves most directly Must still be checked
Uniform random image split Image-ID disjointness if implemented correctly Rare labels, combinations, shared source groups
Combination stratification Common presence-vector proportions Singleton combinations, marginal support after rounding, source groups
Iterative multi-label allocation Marginal label support where feasible Specific co-occurrences, source groups, integer constraints
Group-aware allocation Separation of known related sources Rare labels and combination support, group definition

A practical priority order is independent source group → complete image and its four rows → label support → finer combination proportions. If group metadata is absent, say what you used as a proxy and inspect near duplicates. A filename convention can be useful evidence for grouping, but a different filename alone does not prove independence.

Quantify split luck without promising exact support

For a uniform random holdout drawn without replacement, let the dataset contain N independent images, K positives for a label, and n held-out images. If X is the number of held-out positives, then

\[E[X]=nK/N,\qquad \operatorname{Var}(X)=n\frac K N\left(1-\frac K N\right)\frac{N-n}{N-1}.\]

The last factor is the finite-population correction. It matters because drawing a positive image leaves one fewer positive for later draws. A binomial calculation uses np(1−p) and behaves as if every draw were independent with replacement. It is an approximation, generally with a larger variance when the holdout is a sizable fraction of the dataset. This calculation describes uniform random splitting, not the distribution produced by a stratification rule.

Use another invented example: N=40, K=10, n=8. The expected support is 8×10/40=2. The exact without-replacement variance is 8×0.25×0.75×(32/39)=1.2308, so the standard deviation is about 1.1094. The binomial approximation gives variance 1.5 and standard deviation 1.2247. Both centre at 2; neither guarantees a realised count of 2. The exact probability of zero positives is

\[P(X=0)=\frac{\binom{30}{8}}{\binom{40}{8}}\approx 0.0761.\]

That is about a 7.6% chance in this toy setting. A 20% target does not itself prevent an empty rare-class validation group. If zero positives are observed, a foreground-only Dice for that class has no positive pairs to average. Report it as unavailable with support zero; do not silently assign a perfect or failed foreground score. An all-pair metric could still be defined through empty-pair conventions, but it answers a different question.

For each real split, print realised counts, not just E[X]. Repeat a split under several seeds only as a stability audit: note how support and conclusions vary. Do not try seeds until one produces the best model score and then claim it was a single prespecified evaluation. If a few sources dominate the dataset, repeated image-level splits can keep leaking across source groups; repairing the unit of independence comes first.

Draw the boundary around fitting, selection and final assessment

Training can read the training inputs and targets to update weights. It can also estimate a normalisation mean, sample weights or a spatial-prior map, but those fitted quantities must use training data alone. The validation input is transformed using the already fixed rule; its target is read for measurement and choice. Even without gradients, copying validation masks into a prior map or using their intensity statistics to standardise training is fitted-data leakage.

Development decisions use validation information. A threshold chosen because it wins among five candidates, an epoch chosen because its validation loss is lowest, or a component-size rule chosen after viewing validation masks all use validation. This is legitimate selection if declared, but the same validation score is optimistically selected. Repeating many unrecorded sweeps can overfit that holdout. A final independent test, if available, evaluates the completed rule once under its stated protocol. Hidden test labels or leaderboard feedback should not become a substitute training or threshold-tuning set.

Write a small decision ledger before running an experiment: fixed split ID, candidate choices, metric and tie rule. Afterwards record every attempted candidate and the selected one. If the validation set has just one positive for a class, a single example can reverse candidate rankings; prefer a cautious conclusion to false precision. If no final independent evaluation is available, label the result a validation estimate with its support and selection history.

Core · Audit a split, then keep it fixed

train_ids = set(train_table["image_id"])
valid_ids = set(valid_table["image_id"])
assert not (train_ids & valid_ids)
assert train_ids | valid_ids == set(all_table["image_id"])

Set equality checks coverage and disjointness, but duplicate rows still need their own check. Also record:

  • Number of source images and, where known, acquisition groups per partition.
  • Positive count for each class and count for each label combination.
  • Label-empty images and empty image–class pairs as separate quantities.
  • Partition proportions and any rare-stratum exceptions.
  • Seed, source CSV identity and the saved list of image IDs.

Save the split IDs, not only the seed. Different file ordering or library behaviour can otherwise produce a different allocation from apparently similar code. Use the same split when comparing baselines so a change in validation difficulty is not mistaken for an improvement.

Core · Fit, transform and choose have different boundaries

Training-only fitting includes learned normalisation statistics, a spatial-prior baseline and any learned model. Apply the resulting fixed transformation or rule to validation images. A declared conversion from confirmed 8-bit intensity to 0–1 does not estimate a statistic from the validation set.

Choosing a threshold using validation targets is allowed for model development, but its chosen validation score is then a selection score. Do not present it as a fresh independent test. Choose from a small, predeclared set of candidates, keep a record of the comparison, and reserve an untouched final evaluation when one is available. Do not choose the split seed that makes your model look best.

Checkpoint · Decide what leaks

  1. Two crops from the same photograph go to different partitions. Is a filename-disjoint check enough?
  2. Four class rows from one image are randomly assigned separately. What has gone wrong?
  3. A combination occurs once. Can stratification guarantee its presence on both sides?
  4. You calculate a mean image intensity from training plus validation, then use it for standardisation. What should change?
Hints and explanations
  1. No. Their source photograph must remain on one side; different crop filenames do not establish independence.
  2. The unit of splitting was an annotation row rather than the source image. Rebuild the split at image level.
  3. No. Report the limitation and apply a declared policy without duplicating it across partitions.
  4. Estimate the mean using training images only, then reuse it unchanged. The validation set should not influence fitting.

Optional extension · Check the assumption behind the formula

The hypergeometric formula above supposes N distinct, equally eligible images and a simple uniform sample of n of them. If a camera captures twenty near-identical frames from one scene, they may be twenty filenames but not twenty independent observations. A random image holdout can then contain nearly the same scene in training and validation. The formula still describes how many filenames with a label land in the holdout, but it does not quantify uncertainty over unseen scenes. Redefine the draw at the scene or acquisition-group level where that relationship matters.

A useful audit starts before modelling: compare metadata such as source identifiers and acquisition times; inspect a small set of nearest-looking images from opposite partitions; and check whether crop coordinates or processing suffixes reveal common parents. Perceptual image similarity can flag candidates for human inspection, but a similar-looking cloud need not be a duplicate, and unrelated filenames can still derive from the same source. Document the evidence and the resulting group rule. Never claim that a disjoint-ID assertion alone proves generalisation to new sources.

For deeper study, the original multi-label stratification paper discusses balancing label evidence; it does not override source-group independence. The practice notebook uses a fixed random image split for a short CPU exercise, prints the class-support table and saves the actual IDs. Its fixed seed enables repetition, but the small diagnostic sample does not establish robust rare-class performance. Apply the grouped and stratified reasoning here when designing a full study, and explain any missing metadata.

Decision exercise. Suppose eight images are four before/after pairs from four acquisition sessions. Two sessions contain the rare label, and the validation budget is two images. An image-level split could put the “before” frame in training and the “after” frame in validation, producing two apparently distinct filenames. A session-level split allocates both frames together, so a two-image validation set contains one complete session. If both rare sessions are placed in training, validation cannot measure rare-positive performance; if one rare session is held out, support is one independent source, even though it contains two images. State that support in both units. Which constraint should decide the split? Independence comes first. Then examine whether the chosen independent allocation supplies enough label support for the question you want to answer. A metric printed over two related frames does not create two independent rare-label cases.

Transfer question: identify the true independent source unit for another dataset: image, patient, manufactured item, video or acquisition batch. What evidence would you need before claiming there is no leakage?
